# AccessViz — Semantic Chart Description Benchmark

A research tool for evaluating whether LLMs can generate chart descriptions that preserve **semantic meaning** and **real-world significance** (L4) when accessibility metadata is progressively reduced.

---

## Research Motivation

Current accessible chart tools (Olli, Chartability) test structural accessibility — keyboard navigation, ARIA markup, screen reader compatibility. They do not test whether the *meaning* survives.

Prior work motivates this gap:

- **Playing Telephone** — LLMs lose data relationships and fabricate context across generation iterations
- **Before I Asked My Mom** — visual content (charts, dashboards) connects to real-world stakes; accessible descriptions must encode that significance, not just visual appearance
- **Zong et al. (Olli)** — LLMs can identify domain-specific groupings when given proper scaffolding, but require semantic context, not just visual description
- **Chintalapati et al. (ASSETS 2022)** — even in HCI publications, only 31% of chart alt texts contain trend information and virtually none encode real-world significance (L4)

**This benchmark asks:** given a chart and some accessibility metadata, can an LLM generate a description that a blind user would find not just *accurate* but *meaningful* — grounded in why the data matters?

### The Four-Level Model (Lundgard & Satyanarayan)

| Level | Content | Example |
|-------|---------|---------|
| L1 | Chart construction — type, axes, encodings | "A bar chart with Country on x-axis and Vaccination Rate on y-axis" |
| L2 | Statistics and relations | "Israel leads at 62.4%; mean across countries is 48.5%" |
| L3 | Trends and patterns | "High-income countries cluster at the top" |
| **L4** | **Domain significance — real-world stakes** | **"The gap drove the COVAX equity debate; lower-vaccinated populations faced continued variant emergence"** |

VisText (the primary dataset) explicitly stops at L3 and notes L4 as future work. This benchmark fills that gap.

## Data Model

Each chart in `charts.json` follows this schema:

```json
{
  "chart_id": "vistext_001",
  "source": "vistext",
  "chart_type": "bar",
  "domain": "public_health",
  "image_path": "vistext/images/vistext_001.png",
  "title": "COVID-19 Vaccination Rates by Country (2021)",

  "metadata": {
    "alt_text": "...",
    "aria_label": "...",
    "aria_describedby": "...",
    "olli_tree": "...",
    "scene_graph": { },
    "data_table": [ ],
    "vega_lite_spec": { },
    "l1_caption": "Chart construction description",
    "l2_caption": "Statistics and relations",
    "l3_caption": "Trends and patterns",
    "l4_caption": null,
    "domain_context": "Paragraph about real-world stakes",
    "stakeholder_context": "Who uses this data and why",
    "source_url": "..."
  },

  "ground_truth_description": {
    "context": "...",
    "semantic_meaning": "...",
    "real_world_significance": "..."
  }
}
```

`null` fields are displayed as grayed-out (unavailable) checkboxes in the UI. Only non-null fields are sent to the LLM.

## How It Works

### Accessibility feature ablation

On the chart detail page, each metadata field is a checkbox. Checking a field includes it as a structured block in the LLM prompt. This lets you test:

- **Variant 1 (rich)** — all available features checked
- **Variant 2 (moderate)** — only L1 caption + alt text
- **Variant 3 (minimal)** — image only (vision models)
- **Variant 4 (none)** — no metadata, no image

### Prompt structure

`prompt_service.py` builds a prompt grounded in the four-level model:

```
You are an accessibility expert and data storyteller...
[chart info block]
[metadata blocks for each enabled feature]
[image if included]

Write a description that encodes L1 construction → L2 statistics 
→ L3 trends → L4 real-world significance.
```

### Output storage

Each generation is saved as `data/outputs/runs/<chart_id>/<output_id>.json` containing the full prompt used, generated description, token counts, latency, model ID, and enabled features. No database needed — outputs are loaded from disk by the API.

## Loading Data

### VisText (primary dataset)

The VisText files should be placed inside `data/datasets/vistext/` with this layout:

```
data/datasets/vistext/
  images/           ← rasterized PNG charts  (numbered 1.png, 2.png, …)
  scenegraphs/      ← JSON scene graphs       (1.json, 2.json, …)
  vl_spec/          ← Vega-Lite specs         (1.vl.json, 2.vl.json, …)
  tabular/
    data_train.json
    data_test.json
    data_train_altseed.json
    data_test_altseed.json
    L2L3_captions.json
```

Once the files are in place, run the converter from the repo root:

```bash
python3 scripts/convert_vistext.py
```

This produces two files:

| File | Contents |
|------|---------|
| `data/datasets/vistext/charts.json` | All 8,822 converted charts |
| `data/datasets/vistext/charts_subset.json` | 150-chart curated subset, balanced across chart type and domain |

**What the converter does:**
- Reads `data_train.json` + `data_test.json`, de-duplicates by image ID (keeps first L1 caption variant per image)
- Pulls the higher-quality L2/L3 captions from the separate `L2L3_captions.json` file
- Loads the full JSON scene graph and Vega-Lite spec for each image
- Parses the text-format data table into a structured array (known limitation: multi-word date labels like "Dec 31, 2005" may split incorrectly — the LLM can still read the values)
- **Chart type** is read from `L1_properties[0]`; VisText only has `bar`, `line`, and `area` — `area` is mapped to `line` since they share the same semantic structure
- **Domain** is inferred from the chart title using keyword matching across 6 domain categories; unmatched titles fall to `general`
- The curated 150-chart subset is sorted by metadata richness (scene graph + L2/L3 caption + Vega-Lite spec) then balanced across (chart_type × domain) groups

**Metadata coverage after conversion:**

| Field | Coverage |
|-------|---------|
| `scene_graph` | 8,822 / 8,822 (100%) |
| `vega_lite_spec` | 8,822 / 8,822 (100%) |
| `l1_caption` | 8,822 / 8,822 (100%) |
| `l2_caption` | 8,822 / 8,822 (100%) |
| `data_table` | 8,608 / 8,822 (98%) |
| `l4_caption` | 0 / 8,822 — **annotation target** |

**Domain distribution (full set, keyword-inferred):**

| Domain | Charts |
|--------|--------|
| general | 3,244 |
| finance | 2,698 |
| demographics | 691 |
| public_health | 689 |
| employment | 351 |
| climate | 140 |
| education | 126 |

To use the curated subset instead of the full set, copy or symlink:
```bash
cp data/datasets/vistext/charts_subset.json data/datasets/vistext/charts.json
```
Then restart the backend (it caches the JSON on startup with `lru_cache`):
```bash
touch backend/app/services/dataset_service.py   # invalidates the cache on reload
```

### Olli Gallery (22 charts)

All 22 Olli gallery charts can be loaded automatically using two scripts.

**Step 1 — fetch specs from GitHub** (requires Node 18+, no extra packages):

```bash
node scripts/fetch_olli_specs.mjs
# → data/datasets/olli/raw_specs.json
```

This fetches all 22 TypeScript spec files from the Olli GitHub repo, strips the TypeScript wrapper, and saves the Vega-Lite specs to JSON.

**Step 2 — render PNGs and build charts.json** (requires `vl-convert-python`):

```bash
# Install the rendering library (once):
backend/.venv/bin/pip install vl-convert-python

# Run the converter:
python3 scripts/convert_olli.py
# → data/datasets/olli/images/<id>.png  (22 rendered PNGs at 2x scale)
# → data/datasets/olli/charts.json
```

**What you get after running both scripts:**

| Field | Coverage |
|-------|---------|
| `image_path` (PNG) | 22 / 22 (rendered by vl-convert) |
| `vega_lite_spec` | 22 / 22 |
| `data_table` | 22 / 22 (extracted from inline Vega-Lite data) |
| `source_url` | 22 / 22 (link to Olli gallery page) |
| `domain_context` | 22 / 22 (the description field from each spec) |
| `olli_tree` | **0 / 22** — must be added manually (see below) |

**Adding `olli_tree` manually:**

The ARIA navigation tree is generated at runtime by the Olli JavaScript library — it is not present in the static spec files. To capture it for a chart:

1. Open the chart at `https://umwelt-data.github.io/olli/gallery/#<chart-id>`
2. The Olli ARIA tree appears below the chart
3. Copy the tree text and paste it into the `olli_tree` field in `data/datasets/olli/charts.json`

Then restart the backend to reload:
```bash
# Ctrl+C the running server, then:
backend/.venv/bin/uvicorn app.main:app --reload
```

## Development Notes

### `npm run dev` vs `npm run build`

Only use `npm run dev` during active development. Running `npm run build` writes a production `.next/` cache that conflicts with the dev server. If you accidentally run `npm run build` and the dev server breaks with `MODULE_NOT_FOUND` errors, fix it with:

```bash
rm -rf frontend/.next
# then restart:
npm run dev
```

### Restarting the backend after data changes

The backend loads `charts.json` once at startup. If you re-run `convert_vistext.py` or change any `charts.json` file, restart uvicorn to pick up the new data:

```bash
# Ctrl+C the running server, then:
cd backend
.venv/bin/uvicorn app.main:app --reload
```

You'll see a log line like `[dataset_service] vistext: 8822 charts loaded` confirming the new data was read.

## Adding a New Dataset

1. Create `data/datasets/<source>/charts.json` following the schema above
2. Place chart images in `data/datasets/<source>/images/`
3. Add the source name to `SOURCES` in `backend/app/services/dataset_service.py`
4. Add display metadata to `SOURCE_META` in `frontend/app/datasets/page.tsx`
